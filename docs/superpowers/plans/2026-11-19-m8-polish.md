# M8 Polish: deferred minors from M5 and M6 — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Close the review findings deferred from M5 (ask) and M6 (frontend), so the app behaves well at the edges a reviewer of the portfolio would try.

**Architecture:** No new parts. Each task changes one existing unit and its tests:
- Ollama adapter error messages.
- A body limit on `/ask`, through the existing `BodySizeLimit` middleware.
- Verification of lead-in lines before a list.
- Compose, smoke and README.
- Three frontend units: history, uploads, and the SSE reader with the streaming answer.

**Tech Stack:** as in M1–M7 (FastAPI, httpx, pytest; React 19, Vitest, Testing Library).

**Spec:** `docs/superpowers/specs/2026-11-03-fontes-design.md`. The deferred items are in the M5 and M6 ledgers and in the owner's deferred list.

## Global Constraints

- A test first for every change, watched failing. `mypy --strict`, ruff, oxlint, `npm test` stay green.
- Commits show only the user's account and carry no AI attribution trailer.
- No new dependencies.
- Anti-goal from the spec: never present an uncited answer as supported. The lead-in rule (Task 3) may only lend citations that the list after it really has.

## Out of scope (ruling)

The deferred item "api logs `Future exception was never retrieved … socket.gaierror` while RabbitMQ is unreachable" did not reproduce:
- not on Windows with an unresolvable host;
- not on the stack with `rabbitmq` stopped.

What the stack logs instead is aio-pika's own reconnect log ("Connection attempt … failed … Reconnecting after 5 seconds"). That log is useful and is left as it is.

## Review Focus

1. **A list that follows a lead-in line, where only some items are cited.** The lead-in must count as supported only if at least one item of that list is cited, never by default. Test: `test_lead_in_without_cited_items_stays_unsupported` (Task 3).
2. **A huge `/ask` body (megabytes of JSON).** It must get a JSON 413 before the body is parsed, while a normal question is unaffected. Tests: `test_ask_body_over_the_limit_is_413` and the existing ask tests (Task 2).
3. **The history after a failed fetch.** The sidebar retries by itself. Clicking the same entry again reloads it. A new answer becomes the highlighted entry without re-fetching the answer it already shows. Tests in Task 5.
4. **An upload that fails.** The chosen file stays, so the user can retry. Both buttons are disabled while a request runs, so a double click sends once. Tests in Task 6.
5. **A CRLF stream whose `\r` and `\n` arrive in different reads.** It must not end an event early or drop one. Test: `parseSse` with chunks `['event: token\r', '\ndata: {}\r\n\r', '\n']` (Task 7).

### Task 3: A lead-in line before a cited list

**Files:**
- Modify: `backend/fontes/application/verification.py`
- Test: `backend/tests/application/test_verification.py`

**Interfaces:** `verify(text, source_count) -> Verification` is unchanged. A paragraph's `citations` may now be lent from the list that follows it.

The rule: a paragraph is a **lead-in** when all three hold:
- it is not a list item;
- it has no valid marker;
- its text ends with `:`, and the next paragraph is a list item.

A lead-in takes the union of the citations of the run of list items right after it, in order of first appearance. If none of them is cited, it stays unsupported.

- [ ] **Step 1: Failing tests**
  - `test_lead_in_takes_the_citations_of_its_list`: `"Here is how:\n\n- Fill it [1].\n- Boil it [2]."` with 2 sources gives label `supported`. The lead-in paragraph has `citations == (1, 2)`, and its text is unchanged ("Here is how:", with no marker added).
  - `test_lead_in_without_cited_items_stays_unsupported`: `"Steps:\n\n- Fill it.\n- Boil it [1]."` gives the lead-in `(1,)`, item 1 `()` and label `partially_supported`. Also `"Steps:\n\n- Fill it.\n- Boil it."` gives everything unsupported.
  - `test_colon_not_followed_by_a_list_is_not_a_lead_in`: `"Note:\n\nPlain text [1]."` keeps the first paragraph unsupported.
- [ ] **Step 2:** Run them. Expected: FAIL.
- [ ] **Step 3: Implement.** Run a pass over the cleaned paragraphs in `verify`, before the label is computed. `_split` already knows which paragraphs are list items. Carry that flag along (for example, return `(text, is_item)` pairs) rather than re-matching the cleaned text.
- [ ] **Step 4:** Run the full backend check. In README "How verification works", add a bullet: "**Lead-in lines.** A line ending in `:` right before a list ("Here is how:") counts as supported if the list cites a source." Commit: "A lead-in line before a cited list is supported by that list".
